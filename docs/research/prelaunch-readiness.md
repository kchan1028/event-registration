## Executive recommendation

Complete reliable recovery and staff operation before adding checkout features. The inspected application has useful safeguards: atomic reservations, authoritative payment confirmation, independent readiness states, restricted check-in, repeat-safe bib issuance and timestamped exports. Those implementation facts do not establish live-payment or race-day readiness.

First correct or disprove the reservation retry identity risk and fix details-form focus recovery on main. Close the existing provider-concurrency and mobile-header issues. Next prove the signed-provider failure/reconciliation paths, resolve the already-open merchant, waiver, licensing and retention decisions, and rehearse a mock weekend with named staff, the actual timer and a printed fallback. Keep organizer MFA at the existing final pre-launch security gate. Start with the roadmap's smaller controlled cycling pilot; Berkeley Omnium stays on its existing service until the gates pass.

Beginner category help, clear multi-race totals and paid-versus-ready confirmation deserve validation after these integrity problems. Do not automatically add family carts, alternative payment methods or offline synchronization to MVP. This assessment required no interviews, surveys or live traffic; existing participant-validation gates remain open.

## Proposed launch measurement specification

This is the single proposed measurement protocol for this assessment. Instrumentation below is **not implemented analytics**. Use synthetic manual/replay logs now; preserve the existing [success measures](../../product.md#success-measures) and Phase 1 validation gate. Returning signed-in checkout under three minutes, standard check-in median under 30 seconds/P95 under 90 seconds, zero integrity failures, correct exports and independent staff operation are targets, not results. Workload improvement requires a comparable baseline. Expert scenarios do not satisfy the existing five racer/parent, two organizer and two volunteer validation requirement.

An **order** is one checkout, an **entry** one rider/category, and a **rider** may have linked orders and entries. Count linked rider keys for people, entry IDs for places, order IDs for checkouts and transaction/refund IDs for money. Package lines and replayed notifications are not additional people or charges. Use matured cohorts, showing pending/unresolved separately; do not label every expired hold abandoned.

| Proposed event / exact trigger | Truth, unit and denominator | Metric / synthetic verification |
|---|---|---|
| `event_viewed`, detail rendered; `registration_started`, explicit start | Client session/event; distinct started sessions / viewed sessions | Navigation diagnostic, no current conversion claim. Refresh suppression and mobile/desktop scripts. |
| `selection_reviewed`, client selection/price preview; `selection_rejected`, server order-creation validation rejects | Client preview attempts and server reservation attempts are separate denominators; server rejections / server reservation attempts, reason enum | Verify shared client preview and authoritative server validation/price at order creation against configured rules. No separate quote endpoint or new MVP service is implied. |
| `order_reserved`, committed hold; `checkout_redirected`, attached provider session | Server order/attempt; redirected orders / reserved cohort | Lost-response/refresh dedup returns one logical order. |
| `payment_outcome_recorded`, verified notification; `registration_confirmed`, entries committed | Server payment/order/event IDs; confirmed orders / matured reserved orders | Confirmation latency, paid-unconfirmed and duplicate-charge incident count; duplicate/delayed/out-of-order replay. Client return is not truth. |
| `reservation_expired`, effective expiry/release observed | Server order; unconfirmed expired orders / matured reservation cohort | Controlled clock, pending/reconciliation distinguished; never automatic abandonment attribution. |
| `confirmation_viewed`; `requirement_completed`, authoritative transition | Client order view; server entry state; ready entries / active confirmed entries | Receipt access without email; blocker reasons and resolution age, not paid-equals-ready. |

Existing timing in [CheckIn](../../src/web/CheckIn.tsx), [server check-in](../../src/server/checkin.ts) and [shared check-in](../../src/shared/checkin.ts) starts at first keystroke/scan into an empty search and retains first plausible successful duration. Missing/interrupted/failed attempts and durations over ten minutes are excluded. It measures a subset of successful attempts, not queue time, and does not reliably separate exceptions below ten minutes. Report sample coverage and exclusions alongside median/P95 and separately classify exceptions in rehearsal notes.

Proposed replay identity: one logical attempt/order key per recoverable submission; deduplicate outcome events by authoritative provider event ID and transitions by entity/version. Registration lead owns journey/blocker review, treasurer reconciliation, timer liaison version acknowledgement, technical/support leads failure routing. Actual people, alert thresholds, access and retention require owner decisions before collection. A manual synthetic sheet is sufficient; no analytics service is selected.

Allowlist event/version/reason enum, timestamps, attempt ID and restricted opaque keys only as needed. Those keys remain personal data. Exclude names, emails, DOB, license/emergency details, signatures/waiver text, form contents, free-text errors, full URLs, check-in codes, secrets and card data. Restrict operational joins, aggregate product dashboards, approve retention/deletion and reuse authoritative financial/audit records rather than creating a second ledger. Verify forbidden-field absence and replay counts before any real-data instrumentation.

### Local public event read contention

November 18, 2026, at application commit `cea5ef4`. The experiment ran in one Fastify process on an ARM64 Mac with Node 24.21 and local PostgreSQL 17.12. Fastify injected GETs through the real event-detail route. Each of five rounds used a new disposable database, an application pool of ten connections, and two published fictional demo events with seeded test entries removed. The first event retained one paid two-race order for the simulated cancellation case. One GET warmed each event before the timed trials.

Each round ran 32 serial GETs, then 32 concurrent GETs for one event, then 16 concurrent GETs each for two events, then the one-event burst alongside a same-event order hold and, separately, a simulated race cancellation. Every concurrent trial included one additional read of the second event. The hold targeted the unaffected race and was released after its trial. Cancellation used a fresh reviewed plan and was followed by a GET that verified the closed category. There were 820 measured GETs (800 primary reads and 20 probes), five successful holds and five successful cancellations. All measured GETs returned 200.

| Workload | GET p50 / p95 (ms) | p95 range (ms) | Peak busy / queued / advisory-waiting | Second-event probe (ms) | Concurrent write (ms) |
|---|---:|---:|---:|---:|---:|
| Serial, one event | 3.79 / 4.97 | 4.35–5.69 | 1 / 0 / 0 | | |
| Burst, one event | 90.79 / 136.23 | 134.84–153.10 | 10 / 23 / 9 | 104.92–131.57 | |
| Burst, split across two events | 29.96 / 53.72 | 51.92–153.84 | 10 / 23 / 8 | 54.55–158.51 | |
| Burst plus order hold | 48.76 / 99.75 | 91.41–125.65 | 10 / 24 / 9 | 72.36–100.22 | 103.84–140.41 |
| Burst plus simulated cancellation | 57.39 / 113.94 | 102.23–121.16 | 10 / 24 / 9 | 79.34–99.34 | 150.02–163.98 |

GET percentiles are medians of the five per-round percentiles, with nearest-rank percentiles over the 32 primary reads per round. Other columns show ranges or maxima across rounds. The additional GET is a distinct-event probe in the one-event bursts and shares a targeted event in the split burst. The application pool counters and advisory wait count from `pg_stat_activity` were sampled together with a short timer (2ms requested between queries). The observer collected 21–56 samples per trial. Peaks can occur at different instants, and sampled peaks can miss short waits. The client measured request completion without browser or network delivery time. No standalone write baseline was collected.

The one-event burst occupied every connection while up to nine sessions waited on the advisory lock. The unrelated-event probe also waited for shared pool capacity. Different events reduced the median p95, with substantial variation across rounds. These short bursts identify contention in the current design. They leave sustained arrival rates, checkout and cancellation effects relative to unloaded writes, realistic database size, network overhead, and multi-instance pool behavior unmeasured.

Keep the exclusive event lock until an alternative proves the same published version, capacity, waitlist and cancellation facts. A shared transaction advisory lock could let public readers overlap while existing exclusive writers retain coordination. It would still let blocked readers occupy pool capacity, and it requires reviewing lock ordering and writer delay. A single consistent snapshot could avoid advisory waits, but it would need to prove equivalence for publication, checkout and cancellation races. Compare any candidate with current behavior using the existing correctness regressions and a matched load run.

**Hosting decision remains open** (November 18, 2026, project owner). Establish the expected opening peak and acceptable p95/error budgets from organizer evidence before setting hosted thresholds. Retain the current lock provisionally. Revisit at the pre-hosting gate with representative event sizes, sustained arrivals, independent readers/writers and hosted pool telemetry. See [issue #195](https://github.com/kchan1028/event-registration/issues/195).

Earlier [design research](design-research.md) retains the broader task comparison. Discovery, mobile, keyboard, fees, actual refunds, check-in and offline behavior were not freshly exercised. Missing public documentation is not evidence of a missing capability.

Reuse the [existing illustrative cost model](customer-launch-strategy.md), not a new forecast. Current standard domestic card pricing is 2.9% + $0.30 per transaction; received and manually countered disputes have separate published fees [S6]. Refund principal reverses receipts; reserve is liquidity; retained original processing must not be counted twice. Merchant/charge type determines fund/refund responsibilities [S7]; account ownership alone does not settle liability. Additional payment methods await the accepted operating model and evidence of need.
