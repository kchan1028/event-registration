## How the pieces fit

- **One app, three layers.** `src/web/` (React, built by Vite) calls the Fastify server in `src/server/` over `/api/...`. Both import the same rules from `src/shared/`, so the browser preview and the server's checks agree. The server is the authority; the browser is never trusted.
- **Entry points.** `src/server/index.ts` starts the server (reads `.env`, creates a missing local database, picks the listen address in `listen.ts`). `src/server/app.ts` `buildApp()` creates every module, registers every route, and applies migrations when the server becomes ready. `src/web/main.tsx` mounts `App.tsx`, which does hash routing (`#/register/...`, `#/events/...`, `#/orders/...`).
- **Data.** PostgreSQL through `src/server/db.ts` (`all`, `get`, `run`, `transaction`, `lock`). Schema changes are appended to the `MIGRATIONS` array in `db.ts`; never edit an earlier entry. Tables are described in [DATA_MODEL.md](../DATA_MODEL.md).
- **Event configuration** is one JSON document validated by `eventConfigSchema` in `src/shared/schema.ts`, saved as a draft and frozen into numbered published versions (`src/server/repo.ts`). A publish that changes the waiver (`waiverChanged` in `src/shared/impact.ts`) needs `waiverChangeReason`. Every publish request needs `reviewed` (the saved draft revision and the live version), so tests and scripts publish through `publishReviewed` (`tests/support/publish.ts`, `e2e/support/publish.ts`) or send both. Orders keep the version they were sold under.

## Constraints that are easy to miss

- **Emergency contact lookup.** `POST /api/events/:id/emergency-contact` needs `emergency.view` and exactly one of `orderId` or `entryId`. The response is only the name and phone. Each success inserts `emergency_contact_views` (account, event, order, time). A missing contact or a registration in another event is 404 and writes no row. Check-in uses `detailsOrderId`, the registration whose details the card shows, and keeps bibs on the rider key. Check-in lists, the roster, CSV exports, and organizer order responses omit the contact; `omitStaffEmergencyContact` also blanks the contact fields' values in a correction and, when there are any, that correction's whole reason. A rider or guardian still receives their own registration. Coverage: `tests/emergency-contact.test.ts`, `e2e/emergency-contact.spec.ts`.
- **Check-in recovery.** After a lost individual check-in response, the desk waits for explicit lookup of the same rider and race day before displaying the bib or allowing another check-in. Coverage: `e2e/checkin-recovery.spec.ts`.
- **Readiness refusals.** A check-in conflict marked `check_in_not_ready` carries the current desk card for the same race day. The desk replaces the stale card, and the server records no bib or check-in. Coverage: `tests/checkin.test.ts` and `e2e/checkin.spec.ts`.
- **Registration search.** `matchesRegistration` in `src/shared/lookup.ts` is the only matcher for the Registrations field and `GET /api/events/:id/orders?q=`. It matches an active bib with the same exact-number rule as check-in, and a license number only as the whole number. Check-in search stays in `src/server/checkin.ts` and does not read license numbers. Order views from `viewsOf` include the order's active bib numbers. Coverage: `tests/lookup.test.ts` and `e2e/checkout.spec.ts`.
- **Walk-up bibs.** The staff mark belongs to an individual confirmed entry. Check-in allows a first desk assignment only for a marked entry on the selected day. A preassigned bib follows normal readiness and check-in. The public checkout link does not set the mark. Coverage: `tests/checkin.test.ts` for audit record retries, and `e2e/walkup.spec.ts`, `e2e/checkin.spec.ts` and `e2e/checkout.spec.ts` for desk and checkout flows.
- **Shared walk-up test kiosk.** `src/web/KioskRegistration.tsx` uses the same checkout and receipt as phone registration and runs the idle warning and expiry. `auth.tsx` keeps kiosk test identity out of browser session storage and `Register.tsx` keeps its draft in memory. Browser coverage is in `e2e/walkup.spec.ts`.
- **Restored checkout focus.** `src/web/checkoutFocus.ts` arms focus only when registration is mounted at the test sign-in request, and `retainCheckoutFocus` keeps that flag if the mount effect runs twice. The registration screen calls it once, from that effect. Coverage: `tests/checkout-focus.test.ts`. `e2e/sign-in.spec.ts` checks where focus lands in the production build, which does not repeat the effect.
- **Staff-assisted race selection.** `src/web/WalkUpChoices.tsx` builds public category suggestions for the check-in day. `Register.tsx` rechecks the published snapshot before the rider can apply them. Both surfaces use `walkUpSelection.ts` for category availability. Coverage is in `e2e/walkup.spec.ts`.
- **Per-event lock.** Any write that can change capacity, holds, bibs, or the ledger runs in `db.transaction()` and takes `db.lock(eventLock(eventId))` first (`repo.ts`). `db.lock()` only works inside a transaction.
- **Case-study load, reset, and first sign-in.** A load holds `demo:case-studies` until the owner grant commits. The grant takes `org-members` for the reserved organization after any event lock that load took. The reset route holds the demo lock across the membership check and the delete. It then takes each of the reserved organization's event locks in sorted id order, then that same membership lock, and only then deletes the organization. Until every server holds the demo lock across the membership check, a reset on an older server can still check membership before a load commits. A first sign-in already holds that membership lock before it writes a membership. Coverage: `tests/case-studies.test.ts`.
- **Reuse the shared SQL.** "Counts toward capacity" is `liveEntrySql`; "a hold still reserving" is `reservedOrderSql` (both in `repo.ts`). Holds expire by time, not by a background job, so status checks compare against the clock.
- **Access checks.** Organizer routes call `requireOrg`/`requireEvent` in `auth.ts`; order routes call `requireOrderAccess`. Someone with no role gets 404, not 403, so IDs cannot be probed. `tests/auth.test.ts` checks that every `/api` route registered in `app.ts` with `app.get`, `post`, `put`, or `delete` needs sign-in unless marked public; a route registered another way is not scanned.
- **Cancellation refusal recovery.** Plan/execution commands commit terminal refusals under the event lock before raising their HTTP failure. Same rejected identity/payload replays unchanged; a new acknowledged intent uses a new identity. Known write failures require a successful write-savepoint rollback. These command methods are top-level transactions.
- **Refund creation recovery.** Normalized request evidence is checked under the order refund lock before caps; provider retries keep the saved refund ID. The finance tab retains its unresolved original payload. Do not rotate identity to resolve an unknown result.
- **Guardian removal.** Private relationship history/removal APIs in `juniors.ts` require another relationship ID, reason and acknowledgement. Migration 31 keeps historical removal evidence unknown. The family lock serializes opposing removals; replay targets only its original grant. Tests: juniors, migrations, orders/auth.
- **Guardian authority.** `junior_guardians` active grants or an audited support-approved claimed rider on an unmerged profile authorize linked order access; shared trusted SQL fragments in `juniors.ts` are reused by auth and orders. Invitation acknowledgement/acceptance is atomic; My registrations uses GuardianInvitations.tsx for recipient acceptance. GuardianManagement.tsx handles invitation creation/cancellation, current access and removal/history, sharing guardianRemovalSchema with the server. Profile claims use profileClaims.ts and the same family lock to audit support approval, end guardians, cancel pending invitations and retire the viewer without changing purchase evidence. Allowlisted support can list one account's approved unmerged claims; that read does not choose a claim or change access. Claims default off until explicit age 18 and support account IDs. New checkout calls requireRegistrationAllowed under the family lock to block a former guardian’s claimed-profile saved name; migration 33 snapshots names for older claims at activation and new claims at insert, so later profile corrections do not rewrite the block; historical grants use the full migration-33 account/profile index, not the active-only index. No invitation email is sent. All family writes use the global family lock (event lock first for order writes). Same-family soft merges preserve grants/evidence; different guardian sets or conflicting viewer emails block the correction. Original placer remains provenance; nonce replay rechecks authority. Tests: juniors, migrations, orders/auth and `e2e/guardian-access.spec.ts`.
- **Waiver acceptance evidence.** New orders snapshot account ID, declared racing age and server time beside the waiver; replay/corrections never reconstruct it. Historical evidence stays null. Tests: orders, juniors and migrations.
- **Paid orders are frozen.** Price, rules, and refund policy come from the order's published version; never reprice from the latest config.
- **States are independent.** Entry, payment, and readiness are separate; a paid entry is not cleared to race.
- **Injected clock and providers.** `buildApp()` takes `now`, `auth`, `payments`, and `email` options. Tests use them; do not read `Date.now()` or environment settings deep inside a module.

- **Public catalog cancellation.** `repo.listPublished` reads published summaries and scope kinds in one statement; the shared `cancellationScopeState` classifier also drives event-level CSV labels. `RegisterIndex` retains event links and labels explicit event versus race/day closure without availability claims. Coverage: cancellation execution/auth/API tests and `e2e/catalog-cancellation.spec.ts`.

- **Local reconciliation evidence.** `src/server/reconciliation.ts` reads linked financial source rows; the existing export route requires ledger permission. `src/shared/lookup.ts` owns `formatOrderNumber` for order views and this CSV. `src/web/registrations/FinanceDownloads.tsx` exposes both the reconciliation evidence and finance summary downloads on published Registrations for ledger roles. Coverage: `tests/reconciliation.test.ts`, `e2e/reconciliation-download.spec.ts` plus exports/payments/refunds/auth/orders/lookup regressions. No provider call or settlement calculation.

- **Protected CSV audit.** The export handlers in `src/server/app.ts` append actor and file scope before sending a prepared CSV. `tests/protectedExportAudit.test.ts` covers metadata, denials, HEAD and audit failure. The generated case-study reset removes only its own audit records.

## Tests and commands

- Unit and API tests: Vitest, `tests/*.test.ts`. `tests/support/db.ts` `testApp()` builds an app on a throwaway database; `tests/support/auth.ts` `fakeAuth()` and `as(email)` fake sign-in. Each throwaway database is cloned from a template made in `tests/support/global-setup.ts`, one clone at a time under `TEMPLATE_CLONE_LOCK`; `tests/test-database.test.ts` covers the clone. Other helpers: `tests/support/cancellation.ts` `cancellationSetup()` (published demo event with a refund policy), `tests/support/membership.ts` `takeOffTeam()` (revision-checked team removal). `tests/health.test.ts` covers `/api/health` through database outages and migration retries. They need the local PostgreSQL server from [local setup](runbooks/local-setup.md).
- Browser tests: Playwright, `e2e/*.spec.ts`, with the local-only test sign-in (`AUTH_MODE=test`, configured in `playwright.config.ts`). `e2e/control-contrast.spec.ts` checks control and label contrast in both themes.
- Which tests to run for a change, and when to run everything: the [test plan](testing/test-plan.md). Commands are listed there and in `package.json`.
- CI (`.github/workflows/ci.yml`) skips the test jobs for documentation-only changes; its Documentation links job (`npm run check:docs`, `scripts/check-doc-links.mjs`) runs on every change.
