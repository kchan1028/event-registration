# Pilot run of the usability kit (November 14, 2026)

The historical license-review note checks below describe the November 14 build. The current desk confirmation requires no typing.


Status: Pilot only. This is **not** Phase 1 evidence. The tasks were run by an AI coding assistant driving the browser, not by organizers, volunteers, or riders, so nothing here counts toward the 90% unassisted-completion gate. Its purpose was to check that every task can be completed in the current app, that the setup steps in [tasks.md](tasks.md) work, and to fix obvious problems before real participants see them.

## How it was run

- App at `origin/main` on November 14, 2026, run locally with a fresh database for each role, as the [setup instructions](README.md#set-up-the-computer-before-each-session) describe.
- Desktop browser window (1024 by 768 pixels), dark theme. Phone-width and daylight checks were not done.
- Every core and optional task in [tasks.md](tasks.md) was attempted, including the setup steps for each role, except the optional daylight task V6.
- Not timed. Check-in speed from this run means nothing, because a script does not hesitate the way a volunteer does.

## Fixed in this change

| Finding | Severity | Change |
|---|---|---|
| In check-in, pressing Enter right after typing or scanning a code did nothing, because the list on screen still showed the previous search. A barcode scanner sends Enter immediately, so scanning would never open the rider. Same for a single name match. | Serious | Enter now looks up the typed text before deciding whether exactly one rider matches ([CheckIn.tsx](../../src/web/CheckIn.tsx)) |
| The rider confirmation for an unreviewed license said "License needs review: not verified yet" with no next step. R4's follow-up asks what the rider would do. | Serious | The item now says to bring the license to the registration desk before racing ([checkout.ts](../../src/shared/checkout.ts)) |
| Every confirmation said "Each entry below lists what is still needed", even when nothing was needed. | Minor | The banner says "Not cleared to race yet" only when something is outstanding, and otherwise says everything is done ([Register.tsx](../../src/web/Register.tsx)) |
| The same-start publish warning joined start group names with "and", and the names themselves contain "and", so it was hard to tell how many groups were involved. | Minor | The warning now gives the count and lists quoted names ([validation.ts](../../src/shared/validation.ts)) |
| "Mark reviewed" stayed disabled with no explanation until the note had 3 characters. | Minor | The button stays enabled and explains what to write ([Registrations.tsx](../../src/web/Registrations.tsx)) |

Each fix was checked again in the browser after the change. Kit changes in [tasks.md](tasks.md): the volunteer setup no longer assumes the example weekend has warnings; it now checks Alex in during setup so V5 works; R3 asks for one parent session without the prefilled demo rider; O1 adds a watch point about finding start groups below the category schedule.

## Watch for in real sessions

Noticed but not changed, because real participants should show whether they matter.

- The rider page says "You qualify" for a category before any license check. R4 tests whether riders read that as "cleared".
- Bundle discounts are split across entries (for example −$5.88 and −$4.12) instead of one "Weekend bundle −$10" line. R2's follow-up should show whether that confuses riders.
- The full-race message says to ask the organizer about the waitlist, but waitlists are not built and no contact is shown.
- In the rider preview, ineligible reasons read "Cat 4 is not one of Cat 3". Watch whether organizers understand it in O3.
- The start-list CSV `rider_id` column holds the order ID. Rider identity across orders is a known gap in [roadmap.md](../../roadmap.md#check-in); ask the timer whether the column name misleads.
- The start group "Edit" buttons on the race page all have the same name, which is harder for screen-reader users. Note it if a screen-reader participant takes part.

## Not covered

Phone-width sessions, the light theme, daylight readability (V6), keyboard-only use, and everything a real participant brings: hesitation, wrong guesses, and wording they do not understand.

## Berkeley weekend case study: code-based expert review

Reviewed November 14, 2026 against `00d4439`. **Expert review and hypotheses, not participant research.** No sessions, interviews, observations of people, or official Berkeley Omnium partnership are established by this review. The historical browser dry run above is separate evidence from an earlier revision; its findings are not automatically current.

### Scope and method

Read the current [feature overview](../../feature.md), [product requirements](../../product.md), [roadmap](../../roadmap.md), [design guide](../../DESIGN.md), this usability kit, and the shared rules, organizer/rider screens, server order/check-in paths, and existing tests. Executed the current shared functions with the combined Berkeley fixture in memory, a pre-race quote date of April 10, 2027, and fictional profiles. This was not a new browser walkthrough or a live registration. Transaction/retry behavior below was inspected in source and covered by existing automated tests, not exercised through a payment provider.

Use the combined [Berkeley Omnium fixture](../../src/shared/berkeleyOmnium.ts): Saturday April 17 road race and Sunday April 18 criterium, America/Los_Angeles. These dates and the inherited schedule are demo configuration, not an approved current event schedule. Fixture update (November 15, 2026): the [standard Berkeley seed](../fixtures/events.md) now publishes the combined Omnium without prefilled entries. This historical review uses the organizer working-copy fixture with synthetic capacity usage, not the empty published seed.

The fixture has $80 road entries, $60 criterium entries, a $130 same-event package, $20 extra category in the same criterium race, zero demo fees, a $15 day-of surcharge, and a 15-minute recovery suggestion. The examples below use the pre-race date, so no surcharge applies. Recalculate on the actual session date and record it; demo window bypass does not disable date-based pricing. No quote here establishes a real organizer fee or federation rule.

### External dependencies and evidence limits

- USAC platform approval and permission for electronic rider/guardian waivers are unconfirmed dependencies. Obtain a written accepted electronic or paper process before sanctioned use; do not infer acceptance from a sample signature. Questions remain in [usac-questions.md](../usac-questions.md), not answered here.
- License integration requires access terms, a freshness policy, and accepted fallback review. No connection exists. Self-reported eligibility, simulated-valid fixtures, and manual notes are not USAC approval.
- Stripe is selected, but hosted checkout, authoritative notifications, refunds, reconciliation, merchant/settlement responsibilities, and live operations remain Planned. No real funds moved in this review.
- Race schedule/field approval, timer acceptance, support ownership, and safe real-device testing are required before the corresponding phase can exit. A code comment asserting promoter permission is not evidence of an official partnership or approved migration.
- The earlier dry run's statement that waitlists were not built is historical: current source includes [waitlist service](../../src/server/waitlist.ts) and rider join/offer UI. Delivery is still manual/simulated. Do not treat the old note as the current capability list.
- The earlier dry run's `rider_id` note is also historical: organizer-confirmed rider linking now provides one rider key across linked orders. Linking occurs after checkout. At the time of this run it did not affect capacity; since November 15, 2026, orders the organizer has linked count as one rider toward shared limits, and orders that are not linked still count separately.
