# Security policy

CycleReg will handle rider contact details, emergency contacts, license numbers, waivers, and payments, so security problems are taken seriously while the build is local and holds fictional data. This file explains what to report, how to report it privately, and which security rules the product is held to.

> **Status: local build with email sign-in, fictional data only.** Every API route except the health check, the public event list, rider event pages, the Stripe webhook (trusted only by its verified signature), and, outside production when `RESEND_WEBHOOK_SECRET` is set, the Resend delivery webhook (trusted only by its verified signature; production refuses that secret, so the route stays off) requires passwordless email sign-in (Clerk, [ADR 0003](docs/decisions/0003-sign-in-and-mfa.md) Phase 2), and organizer routes check the caller's role in the event's organization on the server (`src/server/auth.ts`, `src/shared/roles.ts`). Data is stored in a local PostgreSQL database ([setup](docs/runbooks/local-setup.md)). There is no deployed website, no payments with real money, and no real rider data. Payments are simulated or use Stripe test mode; live keys are refused. Email sign-in is one factor: anyone who controls an account's inbox can sign in as it. So the app must not hold real rider data or take live payments until MFA and sensitive-action re-verification are enforced for every organizer role at the final pre-launch security gate; riders and guardians stay on email sign-in by owner decision; until then hosted use is limited to staging and rehearsals with fictional data, and the [Render deploy](docs/runbooks/deploy-render.md) still waits on its other gates. Unless a section says otherwise, the security requirements below are Planned, not Implemented.

Clerk can activate a session in place when its sign-in window returns to the current CycleReg route. The browser keeps the current page state and the API continues to verify every protected request with Clerk. The [rider sign-in regression check](docs/testing/test-plan.md#rider-check-in-code-retrieval) covers this behavior.

## Clerk session revocation

Revoking a Clerk session prevents it from receiving fresh tokens. CycleReg verifies issued tokens against their validity period on each request. An already-issued token can retain access through its expiration time and the verifier’s five-second clock tolerance. The [Phase 2 development rehearsal](roadmap.md#phase-2--build-the-registration-core) records the observed timing. Organization role removal is separate and applies on the next request.

## Transactional invitation email (Implemented locally)

The server sends organizer invitation emails through Resend only in test mode with a configured recipient list. Keep the sending key in server-only environment configuration and use controlled test inboxes. The request contains the recipient address and invitation text. The app records API acceptance or send failure and keeps delivery evidence separate from invitation role grants. Production mode refuses Resend sends. Outside production, when `RESEND_WEBHOOK_SECRET` is set, a public webhook is trusted only after the signature on the raw body verifies. It records delivery, bounce, or complaint for one matching provider message and does not change the invitation, the role, or payment. Overlapping requests to send the same open stopped invitation without extending it share the same email attempt. A confirmed failure permits another attempt. Settlement for a shared attempt can clear only the stop recorded on it. The delivery event stores no bounce text, subject, or addresses, and the webhook sends nothing. A bounce or complaint also writes `email_suppressions` for that organization: the normalized address already stored on the message, the reason, and that message id. Clearing the stop records the owner and the allowed message. Delivery events still store no bounce text, subject, or addresses. Production refuses that secret, so the route stays off. Retry send is owner-only and names one email attempt. The server checks that the attempt still belongs to the invitation just before it sends, so a stale retry cannot invite, renew, or grant a role. Resend is owner-only, has its own route and names the invitation's revision. It renews only while that revision is current, so a stale Resend cannot invite or grant a role either, and a server from before the route answers 404. A Team screen loaded before this change sends Resend as Add until it is reloaded. Add, Resend, Retry send, Cancel and Remove check ownership again inside the write or just before the provider call, so a request that was waiting when its caller lost ownership changes and sends nothing. A change committed before that stays, and its former-owner caller does not receive the team list. Cancel and Remove are owner-only, have separate routes and name the row's revision. Cancel ends only that invitation, never a role, and Remove only that grant. Both check ownership again under the membership lock, and Cancel shares first sign-in's account lock. Their earlier shared route refuses every request, so a Team screen loaded before that change removes nothing. During a deploy an outgoing server still honors that route until it stops. First sign-in takes each organization's membership lock before that account lock, and the team list holds the membership lock while it reads members, invitations, and history. Until every server does this, a first sign-in on an older server can still commit during that read. The case-study reset takes the reserved case-study organization's membership lock after its event locks and before it deletes the organization. Until every server does so, a reset on an older server can still delete the organization during a first sign-in. The case-study load grants the caller ownership before the load's transaction commits, after any event lock the load took and under the reserved organization's membership lock. Until every server grants ownership there, a load on an older server still commits before its grant, so a reset in between can make the grant answer 500. The reset route holds the demo lock across its membership check and the delete. Until every server holds that lock across the check, a reset on an older server can still check membership before a load commits.

## Expired invitation guidance (Implemented locally)

The signed-in recipient reads only their own latest expiry notices through `/api/rider/expired-invitations`. Authenticated account email scopes organization/role history, without revealing the team or granting access. A later grant of the same role supersedes its notice. Real identity-provider acceptance remains open.

## Organization ownership transfer (Implemented locally)

The server checks that the caller is a current owner and the successor is a signed-in account with a current role in the same organization. Both checks run under the organization membership lock. The transfer adds the successor’s Owner role, removes the caller’s Owner role and records one actor-attributed history entry in the same transaction. A refused transfer leaves membership and history intact.

## Reviewed cancellation plans (Implemented locally)

The owner/finance Registrations screen requests a confirmation-ready preview and records only a reasoned, acknowledged plan. Account identity for recovery comes from the signed-in `/api/me` response. Tab storage keys bind account ID and event ID; unresolved normalized request/review-version data are retained until resolved, then replaced with only a record ID. Refresh retrieves that ID from the server under current authority before showing a positive outcome. Session changes remount the recovery state. These keys are a UI separation mechanism, not encryption or server authorization. No request is automatically resubmitted. A known completed reference that cannot be retrieved may be kept for lookup or cleared locally through an explicit separate review; this never discards an unresolved pending request or replaces server evidence.

Unknown/network/server/identity-conflict outcomes keep the original request and block another confirmation. Only a server-marked `cancellation_plan_not_recorded` refusal clears a failed intent for a new review. A new refusal is committed under the event lock only if neither a success nor an earlier refusal exists. Matching rejected identities replay unchanged and cannot record a plan later, even if conditions clear. Authorization/validation before lookup, identity conflicts and unknown failures do not carry that proof. Malformed local data blocks another record until manual review; blocked storage offers in-memory recovery only and explicitly does not promise refresh recovery. Pending reasons/references in browser storage need the existing privacy/retention operating acceptance before real data. Current event finance checks remain authoritative for every save, retry and historical read. The review form itself executes nothing; the separate simulation panel requires its own eligibility check and acknowledgement.

`POST /api/events/:id/cancellation-confirmation-preview`, `POST /api/events/:id/cancellation-confirmations` and `GET /api/events/:id/cancellation-confirmations/:confirmationId` require current event `payments.refund` authority (owner/finance), including replay and historical reads. The server derives the actor, validates a strict selection/request, a bounded normalized reason and explicit plan-only acknowledgement. Unknown actor/execute fields are refused. The event lock serializes confirmation and per-event request identity; changed details conflict and identical retries retain the original actor, timestamp and evidence without reevaluating the old plan. Read queries constrain both event and confirmation ID. Removing a role ends subsequent reads/replays; already-admitted requests follow the existing request boundary.

A fresh impact is computed under the lock before a new insert. SHA-256 binds its contents plus event-scoped payment-attempt/session/refund metadata, with assessment timestamps excluded and expiry effects retained. The digest is a state guard, not a capability, human-review proof, financial history or settlement evidence. Provider updates can occur outside the lock. Normal confirmation routes only insert/read; the existing owner-only generated case-study reset explicitly removes fixture terminal refusals and confirmations under the affected event locks. Unrelated evidence remains. Direct database administration is not made immutable. Actor/event references restrict deletion, and preview snapshots, actor IDs and reasons require the existing approved retention/support policy before real rider data.

Records return `plan_confirmed` and `executionAvailable: false`. The confirmation APIs change no entry or ledger and send no provider/message request. A separate acknowledged simulation-only execution endpoint consumes a saved plan after fresh checks. Distinct request identities can record distinct reviewed plans; they are not repeat-safe execution identities. Provider/credit cancellation execution must independently enforce its own fresh state, financial, overlap and retry rules. No real-data or live-money gate is closed.

Financial-preflight reads require current event finance authority and an event-scoped confirmation lookup. They return only identifiers, nominal amounts and blocker codes, without rider contacts or provider references. The assessment locks the event and affected order refund-request locks in sorted order; provider/refund updates outside these locks still require fresh execution-time reconciliation. Any provider evidence, refund history or uncertain payment blocks simulated eligibility. Even an eligible response cannot execute or authorize cancellation.

## Local reconciliation evidence export

`GET /api/events/:id/exports/reconciliation.csv` uses the existing `export.ledger` authority (owner/finance), before any financial read or attachment metadata. It exports only selected event-linked source fields, including records on inactive orders; unlinked provider events are excluded. No checkout URL, rider/contact/license/waiver fields, raw payloads, reason/failure text or support evidence is included. Provider references remain protected finance data. CSV formula escaping, no-store caching and existing cancellation labels apply. The read does not call a provider or change financial records and does not prove external settlement. The published Registrations control is hidden without ledger authority, uses the existing authenticated download helper and leaves the server authoritative for every request, including stale screens after revocation. No financial records are put into browser recovery storage; failures offer a download retry. See [Reporting](product.md#reporting).

## Protected CSV audit

Entries, ledger, reconciliation and start-list CSV handlers record the authenticated actor only after authorization and successful preparation. An audit error returns no CSV. HEAD, denied and failed preparations do not create audit rows. The audit tracks generation, since the server cannot confirm delivery or local file persistence. Existing CSV permissions remain in force. Audit data has no application read endpoint and contains no CSV contents, rider details or provider references. Restricted operator access and retention/deletion approval remain gates before real rider data.

## Public cancellation status

The existing unauthenticated event-detail route includes committed scope selections and closed published category IDs. It projects no execution/confirmation IDs, actor, reason, rider, audience or refund evidence. Event locking keeps this projection consistent with the published configuration. Plans/refusals do not appear; no new public route or write authority is added. Public registration labels consume these facts without private lookup or permission changes. Selection/continuation guards are usability controls; server admission remains authoritative. Manual refresh never changes unresolved reservation intent. Protected CSV downloads expose only current closure state and current/historical context in their filename/headers, under existing entry/ledger/start-list permissions. No actor, reason, rider or settlement evidence is added. Data and metadata share the event lock; historical contents are preserved. Protected day-list responses add only event/day closure booleans and cancelled race IDs/names. Each day’s riders and cancellation context share the event lock. Printable notices add no rider/contact/payment fields or permissions and do not authorize bib issuance for cancelled races. The existing public event list adds only none/scoped/cancelled status, using published configuration and committed scope kinds in one database statement. No actor, reason, private execution identity or rider data is projected; plans/refusals remain excluded. No route or permission changes.

Offer links open private details only after sign-in in the browser and use the existing authenticated token lookup. Prefill requires a fresh public cancellation check. Retry leaves any unresolved reservation payload intact.

## Atomic simulated cancellation (Implemented locally)

`POST /api/events/:id/cancellation-executions` and ID-based reads require current event owner/finance authority. A strict plan ID, normalized per-event request identity and explicit simulation-execution acknowledgement are required; actor/time come from the server. Exact replay is historical, with current authorization. Each plan executes once; conflicting identities and overlapping closed scopes are refused. Migration 35 stores the result and closure evidence with restricted event/plan/account references.

The executor takes the event lock and sorted affected refund-request locks, repeats financial preflight and uses existing refund caps. It only executes in simulated mode, refuses all provider/session/event evidence and refund history, and sends no provider or message request. Refund, entry, active waitlist and closure writes roll back together. Existing test capacity and unsettled cases are refused. Durable guards cover hold/checkout, transfer, waitlist, test-entry and late-fulfillment paths. Mixed provider modes across application instances are unsupported for simulation rehearsal; real/provider execution remains gated. Draft save/publish refuses category/race placement changes into or out of closed scopes, preventing stranded active entries or poisoned later plans. Check-in and manual/automatic bib allocation consider only active entries; a cancelled entry cannot become ready because its license was reviewed. Existing check-ins, bib evidence and historical snapshots are retained, not reconstructed or silently erased. Organizer simulation controls use a separate acknowledgement; no general undo or message delivery exists. The owner-only case-study reset deletes execution evidence only for its own generated fixtures before deleting their confirmations.

The protected `GET /api/events/:id/cancellation-confirmations/:confirmationId/execution-check` uses the same read-only executor preparation under the event lock, including retained sorted refund-request locks. It returns point-in-time eligibility or original saved execution evidence for that event/plan. A null execution field is not proof that an earlier request cannot commit. `cancellation_not_executed` appears only after a terminal refusal is committed under the event lock for the normalized identity/payload. Read-only precondition failures can be recorded immediately; known execution refusals after writes require successful rollback of the write savepoint first. Unknown database/commit errors, authorization/validation before lookup and identity conflicts carry no such proof. Migration 36 retains rejected intent, actor/time and original error; delayed copies cannot execute after that rejection, even if a temporary blocker clears. Planning uses the same ledger for its existing no-record code. This is not a blanket classification of 4xx responses.

The screen scopes tab recovery by authoritative server account and event ID, parses untrusted stored intent and safe reference IDs, sends nothing automatically, and verifies saved evidence before a restored positive state. An unresolved request blocks another plan review; retries retain its exact plan, identity and acknowledgement. A verified execution for the same unique plan can resolve recovery with original actor attribution; it does not imply the current operator initiated it. Storage is best-effort, not encrypted authority or durable server storage; corrupt state requires manual review and blocked storage has page-only recovery. Final execution still checks current authority and state.

## Cancellation operational impact preview (Implemented locally)

The Registrations screen shows read-only impact and reviewed-plan controls to owner/finance roles only, using the same server permission. It waits for registration data before mounting, clears results on loaded registration/draft changes or selection changes, ignores older responses, and rejects schedule/preview version mismatches. Every load fetches the published configuration for labels and selections. No cancellation or financial action is exposed; displayed amounts still require reconciliation and a fresh preview. Unobserved external changes can make any snapshot stale, so the screen labels it as point-in-time.

`POST /api/events/:id/cancellation-impact-preview` requires event `payments.refund` authority (owner/finance). Strict published scope validation and the paid allocation rules are reused. The outer transaction holds the event lock across financial and operational reads; nested allocation reads use the same database transaction. The endpoint returns entry/order/waitlist/snapshot identifiers and counts, without contact details, invitation tokens or snapshot contents. Capacity uses a single assessment timestamp for holds/offers and existing distinct-rider rules. It is a hypothetical removal including test reservations, never a promise to resell places. Event-wide snapshot references include removed races; linked live-order waitlist offers remain in the waitlist impact but are omitted from duplicate audience records. This does not deduplicate people across unrelated accounts/orders. It performs no writes/provider/message calls, and requires a fresh confirmation preview before any future execution. Provider changes outside the event lock still require reconciliation.

## Paid cancellation allocation preview (Implemented locally)

`POST /api/events/:id/cancellation-allocation-preview` requires the event organization’s `payments.refund` permission (owner/finance); rider ownership and registration-manager role alone grant no access. The selection schema rejects mixed/unknown scopes and validates race/day IDs against the current published event. Queries constrain both orders and entries to that event, and return entry/order identifiers and financial policy information without rider contacts, DOB or support references.

The preview holds the event advisory lock while reading current published placements and active paid entries; accepted versions/prices remain frozen. Versions and nonfailed refund history are read in batches. An unknown current placement blocks every scope because exclusion cannot be established safely; an absent accepted price line blocks only a selected entry. It reserves no money and sends no provider/message request. Refund history may change outside that event lock; results are nominal allocation information with financial reconciliation always required, never a cap or authorization for a later refund/cancellation. Only confirmed entries on confirmed orders are covered; held/unsettled/historical entries and the operational cancellation workflow remain separate work.

## Refund request recovery (Implemented locally)

The read-only whole-order refund-policy preview requires the same owner/finance `payments.refund` permission as refund creation. It reads the accepted event version and payment/refund state under the per-order refund lock. It reserves nothing, calls no provider and grants no authority to refund; creation still rechecks its existing caps. Rider/guardian status alone does not authorize this preview. The organizer form shows it only to current owner/finance roles for the whole original order payment; it never fills or submits the refund amount. Results are kept only in component memory and discarded when order state, entry status/category/paid allocation, refund history, known payment-list amounts or selected entry scope changes.

New refund POSTs require a client request ID. The existing per-order refund lock and a database uniqueness index preserve one accepted normalized request; identical replay reuses the saved row before cap checks, while changed details are refused. Existing owner/finance authorization applies before replay, and the original requester is preserved. Different deliberate request IDs remain subject to payment/entry caps; this is not cross-device duplicate-intent detection.

Unresolved requests are retained in session storage scoped to signed-in email/order; no card data is stored. Storage includes the organizer reason and financial references, so real-data retention remains a gate. Blocked storage gives in-memory recovery only. New refunds are unavailable while this tab's result is unresolved; loss of refund permission keeps read-only guidance. Provider-unknown refunds stop being sent 23 hours after creation, leaving a margin before Stripe API v1 may prune its key; the amount stays reserved and late signed updates can still resolve it. Finance must reconcile before another reimbursement. No automatic replacement refund, support override or real payment is added.

## Publication audit (Implemented locally)

Each version an organizer publishes records the publishing account from the session, and a reason when the waiver changed. Versions from before migration 43 and case-study scenarios record no publisher; a named demo records the account that loaded it. The server decides under the event lock whether a reason is required and ignores the text of one sent otherwise. Every organizer publish request names the draft revision and live version that were reviewed. An otherwise well-formed request that names neither, or an older one, is refused with 409 before any acknowledgement or reason is considered. Named demo and case-study loaders publish their own seeded drafts directly and take no review. `GET /api/events/:id` sends the publisher's email and the reason only to roles with `event.edit` (owner, registration manager); volunteer, timer and finance roles and every public route get neither. A shared demo's co-owners see each other's emails there, as they already do on Team. Application code never edits these fields. The scoped case-study reset still deletes its fictional versions, and no database trigger enforces immutability. The reason is free text, so the screen asks staff to leave out rider details; retention remains a launch gate.

## Waiver acceptance evidence (Implemented locally)

New orders record the authenticated accepting account ID, validated declared racing age and server acceptance timestamp beside the original waiver. Client-supplied evidence is ignored; checkout replay and rider corrections preserve the original snapshot. Historical records remain null rather than being reconstructed. Existing private order-access rules govern this evidence, including read-only junior viewing; no public field, access override or federation approval is added. Demo/case-study fixture orders, including organizer demo actions, have no inferred accepting account. Preservation is enforced by application writes, not a database immutability trigger. Retention, real identity and legal/minor acceptance remain launch gates.

## Explicit guardian authority (Implemented locally)

Migration 30 promotes active `junior_guardians` records on unmerged profiles to the authority for linked junior orders. The placing account stays provenance; it alone cannot authorize a linked order. Shared SQL controls private order reads, payment/cancellation and registration lists, and checkout nonce replay rechecks current authority. Adult orders without a junior profile retain placing-account authorization. A junior viewer stays read-only. Organization permissions remain separate and never grant family invitation authority.

Private invitation creation/cancellation is available on My registrations through the existing authenticated APIs. My registrations renders recipient lookup and acknowledged acceptance using the existing authenticated APIs; no grant is made by viewing an invitation. Signing in grants nothing; acceptance rechecks invited email, current inviter, expiry/cancellation, guardian count, viewer address and same-name household collision. All family writes share one advisory lock; order writers take the event lock first. Acceptance records actor/time and inserts the grant in one transaction; retries do not add or reactivate grants. No email is sent.

Profile creator identity is nullable provenance. Name merges require identical active guardian sets and compatible viewer emails, preserve source profiles/grants and accepted evidence, and move orders/history to the canonical profile. Linked orders restrict profile deletion. These are application protections, not a database immutability guarantee or proof of legal guardianship. Original payments/waivers remain unchanged. Explicit removal APIs require a current guardian, other relationship ID, reason and acknowledgement; family locking prevents opposing removals from removing both guardians. Identical replay preserves evidence and never targets a later grant. Private relationship history is available only to current guardians. Guardian management screens use the same authenticated APIs and shared removal validation; the current-account label comes from the server account ID, not a comparison of display emails. Support claim approval is Implemented locally and disabled by default; disputed restoration remains Planned; every claim requires product-owner/support approval (owner decision November 17), separately from the explicitly configured minimum calendar age of 18 based on date of birth (owner decision November 17), using the rider’s recorded time zone and March 1 for February 29 birthdays in non-leap years. Support records reviewed birth date and rider-confirmed time zone with a review reference only, without identity-document copies; this does not approve broader retention or real-data use. Missing or invalid recorded time zones prevent claim approval; approved disputed restoration requires product-owner/support review only. Retention/account deletion and real identity/minor-consent approval remain launch gates.

### Support claim approval boundary

`POST /api/support/juniors/:id/claim` requires an authenticated account ID in `PROFILE_CLAIM_SUPPORT_ACCOUNT_IDS` and an explicit `PROFILE_CLAIM_MINIMUM_AGE=18`. Defaults grant no support authority; invalid age configuration fails startup. Operator IDs are snapshotted at startup, so remove an ID and restart to stop its future approvals/replays. Organizer roles, guardian status and viewer login grant no claim approval authority. The claimant must already have signed in, differ from the approver, and not be an active guardian. Inputs require a real calendar DOB, named time zone, reference and acknowledgement; extra document fields are refused. These inputs record the operator’s review, not independently verified legal identity. Reference content is an operating control: staff must use an opaque case reference rather than an identity/document number; the API cannot classify free-text contents.

Under the family lock, one approval row, guardian revocations, pending-invitation cancellations and viewer retirement commit or roll back together. The claimed account controls linked-order rider access; removed family authority cannot replay checkout or restore grants by invitation replay. Approval retries preserve the original actor/time; claim and request uniqueness plus account/profile references constrain evidence. DOB, zone and review reference are not included in ordinary order/profile responses. Audit references restrict deletion, so retention/deletion policy and real-identity/minor-consent acceptance remain gates under issue #170. Requests already authorized before revocation can finish; subsequent family requests are denied. There is no support screen or broad family-recovery override. A distinct new checkout profile does not restore old order access; new junior checkout by a historical guardian is refused for a claimed profile’s same normalized recorded registration-block name under the family lock before any new order insert. This includes grants revoked before the claim and recorded merge ancestors, without an organizer/support-role bypass. It does not infer identity across unrelated households or alter existing accepted orders. The block uses a name snapshot captured at claim insertion (or the migration-33 activation baseline for older claims), not mutable later profile names. No support review queue or unblock endpoint is implemented; real-identity/support operating acceptance remains open in issue #170.

## Reservation recovery (Implemented locally)

The existing per-tab registration draft also retains the exact pending reservation payload, displayed waiver text and public accepted addenda until its outcome is known. The request also carries each accepted addendum's title and text, and under the event lock the server refuses a new reservation whose text is not the published one. The saved review text is separate and is never trusted as acceptance. Older drafts can still retry when this text is unavailable. Unknown network/server, authentication and rate-limit failures retain that request ID; pending entries and consent cannot be edited. Recovery uses the existing account-protected order endpoint and server idempotency checks. A definitive rejection refreshes published terms and clears agreement if the waiver changed. Publishing refuses different waiver text under a version the event already published, and checkout refuses new reservations on a version that older publications already gave two texts, so the server's version check also covers the text. Signatures from before these rules may be ambiguous. Rider replay adds no route, role, database field, logging or card storage. Browser storage remains best effort; blocked storage or closing the tab cannot guarantee refresh recovery. Use fictional data only.

A separate signed-in route, `POST /api/events/:id/reservation-status`, gives staff an event-scoped reservation lookup. It requires `orders.view` and an exact request reference. Lookup refuses references with NUL or unpaired surrogates, which storage would reject or alter. It returns only the saved order number, effective status, active hold expiry, whether staff released it, and whether this caller may release it, with `Cache-Control: no-store`.

`POST /api/events/:id/reservation-release` requires `entries.manage`, confirmation that the rider asked, and a reason. Under the event lock and then the membership lock, both held until it commits, it checks the caller's permission again, then the hold and its payment history. A role removal therefore finishes before the check or waits for the release. It refuses holds with a started provider checkout, other payment evidence, or no tracking from creation, and it never contacts the provider. In production the route refuses every release until an operator sets `STAFF_HOLD_RELEASE=on`. The order keeps the staff account, time and reason. Order responses expose only that staff released it. The reason is free text: staff must not type contact details, and no screen or API returns it. Its retention is open with the other retention decisions.

## Checkout-session retries (Implemented locally)

Concurrent requests use the existing order-scoped provider key and fixed request parameters. The Stripe SDK handles bounded conflict retries; an exhausted `idempotency_key_in_use` conflict returns a retryable 503 without creating a payment or changing entry/readiness state. The same authenticated order can be retried. Session expiry is described in [the data model](DATA_MODEL.md#payment_sessions); it does not extend capacity reservations. A session saved after the rider cancelled is not returned as a payment-page redirect. Who may open checkout is unchanged, and an already open provider page is not expired. Tests use the real SDK with a fake HTTP transport and fictional data, not a real provider account. Live keys remain refused; permissions and webhook verification are unchanged. A signature-verified notification saved before its session row is applied when that row is recorded, and only for that session's order. The webhook stays public and is still trusted only by its signature. A mismatched order reference is not applied.

The check-in QR scanner processes camera frames on the device. Stopping the scanner or leaving its view releases the camera stream, including a stream returned after the view closes while permission is pending.

A readiness refusal includes the current desk card and race day only when the rider has an entry or an active bib in the day’s check-in scope. It uses the same fields as desk lookup, with no private contact details or payment amounts. The server still decides readiness under the event lock before any bib or check-in write.

## Walk-up phone handoff (Implemented locally)

The walk-up marker requires the event’s check-in permission. Under the event lock, the server verifies the confirmed entry belongs to the selected rider and race day and records the staff account and time. Public checkout and the QR/link cannot mark an entry. The server checks for a same-day marked confirmed entry before first bib assignment at the desk and still enforces payment and readiness. Staff views show the marker without exposing its actor.


The basic phone registration QR and address contain only the event identifier. The separate test kiosk address also contains only the event identifier. Registration stays under the participant/guardian account; the staff session is not handed to the rider. No new API route, role, account access, payment method or waiver bypass is added. The published-event guard suppresses handoff for an unpublished event; server registration validation remains authoritative. Local loopback addresses cannot serve another device; real-phone use requires reachable staging with the existing security gates.

### Shared walk-up test kiosk

The kiosk runs only with test sign-in and accepts simulated payment events. Its sign-in, checkout draft and receipt live in the page session and are discarded on session end, reload, or after five idle minutes. The warning in the last minute lets the rider extend the session. An expired kiosk session can no longer display the prior draft or receipt. Riders can check saved orders under their own accounts from a separate device. Test kiosk sign-in does not use the ordinary browser sign-in or its saved draft. Use a dedicated rider browser with autofill disabled. Order access and registration requirements are enforced by the same server rules as phone checkout. Hosted sign-in, hosted payment, and physical kiosk acceptance remain Planned.

### Staff-assisted race selection

Check-in staff can generate a handoff address for the selected day. The address contains the public event and suggested category identifiers. It carries no staff session, rider details, invite or waitlist token. The participant applies the suggestions in ordinary checkout. Existing account ownership, waiver, eligibility, registration window and capacity checks apply.

## What to report

Report privately if you find any of these in the repository, its history, or a pull request:

- A secret, API key, token, password, or `.env` file
- Real rider data, such as names, emails, birth dates, license numbers, emergency contacts, waivers, or payment records (fixtures must be clearly fake; see [CONTRIBUTING.md](CONTRIBUTING.md#how-to-make-a-change))
- A requirement or design in [product.md](product.md) or [docs/architecture.md](docs/architecture.md) that would expose personal data, bypass multi-factor authentication (MFA), or let a role see or change more than it should

Once code exists, report vulnerabilities in it the same way.

General bugs, typos, and feature ideas are not security issues. File those as normal issues following [CONTRIBUTING.md](CONTRIBUTING.md#reporting-a-problem).

## How to report

**Do not open a public issue, pull request, or discussion for a security problem.**

1. Use GitHub's private vulnerability reporting: on the repository's **Security** tab, choose **Report a vulnerability** ([direct link](https://github.com/kchan1028/event-registration/security/advisories/new)). Only the owner sees the report. If you cannot use it, contact the repository owner privately through their GitHub profile ([kchan1028](https://github.com/kchan1028)).
2. Describe what you found, where it is (file and commit, or URL), and how it could be misused.
3. Leave out real personal data. Describe it ("a rider's license number appears in fixture X") rather than copying it.
4. If you found an exposed secret, do not use it to test access.

## What happens next

This is a volunteer project with no response-time guarantee. The owner aims to:

1. Acknowledge the report and confirm whether it is a security issue.
2. Remove exposed secrets or personal data, rotate any affected secret, and record the incident, as required by [docs/coding-guide.md](docs/coding-guide.md#secrets).
3. Fix the document or code and credit the reporter if they want credit.

Please give the owner a reasonable chance to fix the problem before you discuss it publicly.

## Protected bib reassignment (Implemented locally)

Bulk bib changes require `checkin.settings` (owner or registration manager). Individual corrections retain the existing `checkin` permission for check-in staff. Both paths require a reason and a fresh server-verified before/after preview. Changes to checked-in riders also require an explicit acknowledgement bound to that preview; the former direct individual-change endpoint refuses requests without a preview fingerprint. Linked orders resolve to the canonical rider key. Individual corrections may retain an issued bib after refund, withdrawal, or cancellation; authorized lookup includes inactive riders only while they retain an active bib in the selected collision scope. Bulk changes still require confirmed entrants. No financial or entry state is restored.

The server rechecks numbers, ranges, identities, published configuration, and check-in state under the event lock. Conflicts or stale previews apply no changes. Swaps release and replace selected numbers atomically, preserve old assignment rows, record the authenticated actor and reason, and create linked revisions for all affected start lists in the collision scope. Snapshot failure rolls back the entire change. Entry, payment, waiver, license, and check-in states are unchanged. No new public route or contact data is exposed.
